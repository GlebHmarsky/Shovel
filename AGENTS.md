# Project guidance for AI sessions

Read [product](docs/product.md), [requirements](docs/requirements.md), [architecture](docs/architecture.md), [roadmap](docs/roadmap.md), then [TODO.md](TODO.md) before substantive work. They own UX, obligations/tests, technical decisions, milestones/evidence, and the single prioritized implementation checklist respectively. See [README](README.md) for build/run/check commands. Read applicable nested instructions before editing.

- **Confirmed** means requested by the user. **Proposed** is not approval. **Open** requires resolution. **Deferred** is outside the current phase. Never promote a proposal silently.
- Product name: **Shovel**, confirmed 2026-10-24. The main executable is Shovel.exe; internal GitGui project names and the existing settings profile remain for compatibility.
- Application icon: the user-selected front-facing silver shovel on a blue circle (2026-10-25), stored in Assets/Shovel.png and Assets/Shovel.ico under src/GitGui.App; embedded in the executable and main window from 0.4.2.
- Current priority: fast automatic local history before further Git features. The user removed read-approval questions/settings in 0.6.0: opened/restored tabs read automatically. Identity stamps detect replacement; they are not permission to run helpers/hooks/mutations or network fetches. Read the audit and native-launch boundaries in architecture. Retain bounded tab caches and never reduce history scope/page size merely to improve a timing claim.
- Current delivery: F1e / 0.6.0 direct job-contained Git launch, native Git discovery, combined HEAD/ref reads, no history-consent prompt, tab context menu and middle-click close. Final verification is recorded in roadmap/TODO. No interactive launch or desktop control. C# + WPF / .NET 10 LTS is confirmed. The user requests commits of intended source/documentation changes, version increments and matching ignored local previews. No push, installer/updater, hosting, signing or dependency installation is authorized by the preview request.
- The app is intended to be maintained by AI. Prefer understandable modules, mature dependencies, reproducible builds, and explicit state over clever abstractions. TypeScript is excluded. Keep Core independent of WPF; compose services in App, use view models for presentation state and code-behind only for view/lifetime behavior. No external packages are needed for the foundation.
- Inspect existing files and changes first; preserve unrelated work. Keep changes narrow and reviewable. Commit delivered updates as requested. Do not add parallel agents unless explicitly authorized.
- Version each delivered update in Directory.Build.props; use a minor bump for new capabilities, patch for fixes/docs-only deliveries, and deliberate major bumps for incompatible released contracts. Update CHANGELOG.md once per delivery, not per intermediate edit. Build a matching local preview with scripts/Build-Preview.ps1; `/Build/` must stay ignored/untracked. Never overwrite an earlier version folder. Local preview packaging is not signed distribution or an updater.
- Never test destructive workflows against user repositories. Use disposable repositories and isolated Git configuration; obtain task authorization before real launches/system changes or live authentication/network tests.
- Keep Git/process/filesystem work off the UI thread. Preserve safety, trust, localization, privacy, and updater idle-gate requirements during every phase; do not postpone them as polish. Put all app-owned visible strings in Resources/Strings.resx, including errors and accessibility names. Never log arbitrary exception messages, paths, command arguments or repository content.
- Follow [verification gates](docs/requirements.md#verification-and-acceptance). Report what works, evidence, limitations, and next step. Distinguish compilation/unit tests from actual Windows runtime, authentication, accessibility, performance, and installed-update testing. Never present mocks as Git functionality.
- Update the owning document when an approved decision, requirement, phase boundary, or verification status changes. Maintain TODO.md as the only implementation task list; roadmap contains milestone status and evidence, not competing checkboxes. Record verification date and limitations after each phase. Update README when setup/build/run commands change.
- [Research notes](docs/research/fork-ui-observations.md) preserve historical evidence, not normative instructions. Current project documents and direct user instructions take precedence. Recheck changing vendor APIs before implementation.
