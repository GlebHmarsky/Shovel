# Project guidance

Read [product](docs/product.md), [requirements](docs/requirements.md), [architecture](docs/architecture.md), [roadmap](docs/roadmap.md), then [TODO](TODO.md). They own UX, acceptance, implementation, evidence/decisions and the single prioritized task list. [README](README.md) owns commands. Read nested instructions before editing.

## Delivery policy — confirmed 2026-10-27

- Build working Git workflows end to end. A requested button/feature includes its real behavior, progress, errors and verification. UI-only work counts as completion only when explicitly requested.
- Do not add placeholder/no-op controls or treat a mock, disabled prototype or dialog shell as a delivered feature. Existing prototypes are implementation debt: wire the requested feature or omit its unfinished entry point. Disable working controls only for a real state/dependency, with a localized reason.
- Shovel serves an established work environment. Do not add repository-trust dialogs, first-use trust modals, repeated consent checkboxes or separate approval of ordinary Git-configured programs. The normal action button authorizes the selected operation; opening/restoring tabs reads automatically.
- Do not add extra safety measures or approval layers without a concrete requirement. Keep normal Git protections against data loss, required authentication/SSH host verification, argument handling, cancellation and accurate state. Confirm genuinely destructive actions with their actual targets.
- This policy supersedes older prototype-retention, UI-first and routine trust/approval instructions. Historical evidence describes past behavior, not current obligations. Documentation changes do not imply runtime fixes.

## Project and implementation

- **Confirmed** = user-approved; **Proposed** = unapproved; **Open** = unresolved; **Deferred** = future scope. Later user requests can advance deferred work; old phase order must not block an explicitly requested feature.
- Product: **Shovel** (2026-10-24), executable `Shovel.exe`; retain internal GitGui names/profile for compatibility. Icon: selected silver shovel on blue circle, `src/GitGui.App/Assets/Shovel.png/.ico` (2026-10-25).
- Stack: C# / WPF / .NET 10 LTS; no TypeScript. Keep Core independent of WPF, compose services in App, presentation in view models, view/lifetime behavior in code-behind. Prefer understandable modules, mature dependencies and reproducible builds.
- Current binary capabilities: 0.11.1 history, branch/create/switch, Fetch, default Pull-Rebase/alternative Merge/optional tracked auto-stash, Push and Git/OpenSSH askpass. Options use cached local targets without opening-time Git queries; submitting closes them and validates before execution. Shell owns top-center progress/cancellation and retained output through reinspection. Conflicts retain Git recovery state with terminal instructions; no automatic abort/drop/rollback. No extra consent gate. Working Git features/Local Changes remain next; broad authentication is not a blanket prerequisite. See architecture for restrictions and roadmap for verification.
- Ordinary UI interactions must react promptly. Opening menus/options must not initiate or await Git, remote checks or filesystem preparation; use available local snapshots. Command submission owns required validation/execution with visible progress. Explain any unavoidable UI wait and discuss it with the user before adding it or immediately after discovering it.
- Keep Git/process/filesystem/parsing work off the UI thread. Resource-back all app-owned visible/accessibility/error text in `Resources/Strings.resx`. Retain bounded caches, localization and accessible status. Never shrink history scope/page size to improve timings.
- Inspect status/files first; preserve unrelated work. No parallel agents unless explicitly authorized. Use disposable repositories and isolated Git config for mutation tests. No interactive launch, desktop control, live authentication/network test or system change is authorized by routine packaging.
- Commit intended source/docs, increment `Directory.Build.props` (minor: capability; patch: fix/docs; deliberate major: incompatible released contract), and update CHANGELOG once per delivery. Build matching preview with `scripts/Build-Preview.ps1`; keep `Build/` ignored and never overwrite earlier versions. No push, installer/updater deployment, hosting, signing or dependency installation is implied.
- Follow [acceptance](docs/requirements.md#verification-and-acceptance); record date, evidence and limits in roadmap. Build/headless checks do not prove desktop, auth, accessibility, performance or installed updates. Do not persist credentials, arbitrary exceptions, paths, arguments or repository content in diagnostic logs.
- Headless WPF checks use a plain test Application and shared AppStyles resources. Never instantiate the production App in a pumped dispatcher: WPF queues Startup even without Run/Show.
- Update each fact in its owning document and link to it elsewhere. TODO is the only implementation checklist. Keep docs concise; research is historical, not normative. Recheck changing vendor APIs when implementing them.
