# Architecture and distribution

Updated 2026-10-26. **Confirmed stack: C# + WPF**, selected by the user. **Implemented through F2b / 0.9.1:** .NET 10 LTS, MVVM shell, local settings/resources/diagnostics, automatic history, explicit branch/fetch/fast-forward-pull/push actions and operation-scoped Git/OpenSSH askpass. Other designs below remain proposals unless identified as implemented. User obligations live in [requirements](requirements.md); tasks in [TODO](../TODO.md); evidence and unresolved decisions in [roadmap](roadmap.md).

## Product identity

**Confirmed:** Shovel (2026-10-24). Version 0.3.1 uses `Shovel.exe` / `Shovel.dll`, Shovel product metadata and the resource-backed title. Source folders, solution, namespaces, resource base name, infrastructure assembly and manifest identity retain their internal `GitGui` names. The existing settings path and profile mutex remain unchanged to preserve tabs/layout and exclude simultaneous writers across old/new previews. Publisher and permanent installer/data identity remain open; this rename does not add an installer or migrate data.

Version 0.4.2 embeds Assets/Shovel.ico in Shovel.exe through ApplicationIcon and as a WPF resource referenced by the main window. The ICO contains 16, 20, 24, 32, 40, 48, 64, 128 and 256 pixel frames with transparency; Assets/Shovel.png preserves the selected generated source artwork. Conversion uses proportional scaling with transparent padding to keep the artwork square without distortion.

## Stack and boundaries

C# / WPF is confirmed; .NET 10 LTS was selected using the installed SDK 10.0.401 and Windows Desktop pack 10.0.12. The official policy lists .NET 10 support through 2028-11-14; refresh servicing patches before distribution. [Microsoft support policy](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core). Git for Windows CLI is the implemented metadata adapter; no libgit2 dependency. TypeScript is excluded. [Stack research](research/desktop-stack-reassessment.md) preserves alternatives and rationale, not measured performance claims.

Proposed baseline: x64 Windows 10 22H2 and Windows 11; ARM64 later. Confirm actual fleet before claiming support. Runtime compatibility and Microsoft's supported OS editions are separate: [current .NET Windows support](https://learn.microsoft.com/en-us/dotnet/core/install/windows) limits Windows 10 support to particular LTSC/Enterprise editions.

The following are **future logical boundaries**, not six projects already created:

| Boundary | Owns |
| --- | --- |
| WPF UI/view models | Views, command bindings, focus, accessible graph/diff presentation; no Git orchestration |
| Application core | Typed operations, previews, safety/idle gates, immutable snapshots, workflow state |
| Git adapter | Capability checks, command construction, byte parsers, discovery and state queries |
| Windows infrastructure | Process host, prompt bridge, owned descendants, watchers, external-tool tracking |
| Persistence/resources | Versioned settings/session state, caches, diagnostics, localized messages |
| Update coordinator | Scheduling/status, verifier/updater adapter, shutdown handshake; cannot bypass core idle gate |

Keep one primary language, minimal dependencies, pinned SDK/packages, reproducible build/test/publish commands. No embedded web server, plugin framework, or database initially.

App references Core and ProcessHost and packages the AskPass executable; Core never references WPF or Windows process APIs. There are no external NuGet packages. Small INotifyPropertyChanged/ICommand implementations suffice; no command framework, DI container or generic repository/service scaffolding. Add mature dependencies only when a concrete need outweighs owning a small amount of code. Standard WPF controls preserve native keyboard/automation behavior; the graph cell draws already-computed real parent connections.

App creates services explicitly, shows a loading shell, then loads settings on a worker task. Schema 4 restores identity stamps; 0.7.0 ignores saved narrower scope preferences and writes All Commits; the selected repository loads automatically without a consent question. Identity saves are serialized with the settings writer and drained before shutdown; a save failure leaves local history usable and is reported. Closing cancels startup, stops navigation, captures a plain layout snapshot on the dispatcher and saves it off-thread. Saving failure offers stay/retry or explicit exit without saving; normal exit drains diagnostics with a bounded wait. A per-profile mutex prevents two app writers. Dispatcher/startup failures show a resource-backed generic error and exit without saving potentially invalid state; fatal process logging is best effort. No tray, startup network work or background polling exists.

Closing prevents new inspections, cancels the current read and awaits cleanup before saving. In 0.8.0 the entire explicit-action modal/preparation/reconciliation period blocks main-window shutdown and tab navigation. The operation modal cannot close while executing; explicit cancellation drains owned processes and reinspects before exit. A separate named common-directory mutex coordinates Shovel actions across linked worktrees/profiles. This is not yet the future updater/external-tool idle gate; no updater service exists.

## Implemented Git metadata and process execution

Discovery checks standard Git for Windows installation roots or an explicitly selected executable, never PATH/current-directory git.exe. It prefers the native `ucrt64/bin/git.exe`, then `mingw64/bin/git.exe` / `mingw32/bin/git.exe`, with `cmd/git.exe` as fallback. Explicit selection is honored exactly. Native absolute-path invocation avoids the wrapper's extra process and is documented by [Git for Windows](https://gitforwindows.org/git-wrapper.html); [current release notes](https://github.com/git-for-windows/build-extra/blob/main/ReleaseNotes.md) explain the ucrt64 path transition (checked 2026-10-25). No PATH, HOME, global config or installation edits. Version floor stays 2.47.0; only 2.51.1 / mingw64 is runtime-tested here. Custom executable selection is session-only.

### Automatic local history

`WindowsRepositoryIdentity` performs bounded filesystem-only validation before any Git command. Automatic reading supports worktree roots on local fixed drives, with no reparse component in the root, `.git`, resolved Git directory or common-directory paths. UNC/removable/reparse paths and opening a subfolder instead of the root currently require a supported root location; they are not silently followed. `.git` and `commondir` pointer files are bounded at 8 KiB. Fingerprints combine normalized absolute paths, volume serial/128-bit file IDs and creation times for the root/`.git`/Git directory/common directory plus linked-worktree pointer contents. This detects ordinary moves/replacements/redirection, not hostile in-place modification, spoofed/reused IDs, profile tampering or an atomic swap during a read. It is not a sandbox. [Windows file identity](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info) (checked 2026-10-25).

**Policy revised by the user for 0.6.0:** explicit Open and startup/tab restoration read local history without a consent dialog. No read-approval/revocation UI remains. Existing schema-3 approval fingerprints migrate as replacement-detection stamps, not permissions; schema-1/2 and previously unapproved saved tabs load automatically. After the first successful read, save identity for future replacement detection. Every tab activation validates identity off-thread; mismatched/missing/inaccessible targets clear rows and stop. Reopen explicitly binds a replacement without an additional question. Git-reported directories must match filesystem identity, and identity is checked after the read. A first read has no earlier stamp to compare; profile tampering and in-place modification remain outside the guarantees above. Closing removes the tab/stamp, never repository files. Future executable features still require separate trust/workflow gates.

**Automatic-read audit:** only version, rev-parse, symbolic-ref, for-each-ref, log and rev-list are used. rev-list compares validated object hashes with --left-right --count; it requests no files, helpers, hooks or network access. Structured arguments, explicit executable, closed stdin, no pager/optional locks/lazy fetch, disabled fsmonitor/auto-maintenance remain. History explicitly suppresses patches, external diff/textconv, signatures, notes and mailmap. No hooks, filters, credential helpers, editors or transport commands are requested. Repository/global config includes can be read; repo content is not a security sandbox. Inherited Git redirects/traces are stripped except deliberate config locations; Git ownership checks remain active. Test marker helpers and partial-clone missing-object behavior; no automatic fetch/repair. [Git invocation/security](https://git-scm.com/docs/git), [rev-parse](https://git-scm.com/docs/git-rev-parse) (checked 2026-10-25).

Core reads locations once with `rev-parse`, then obtains HEAD, full symbolic branch, upstream ref names and named refs in one `for-each-ref --include-root-refs` observation; this option is present in [Git 2.47 documentation](https://git-scm.com/docs/git-for-each-ref/2.47.0). An unborn HEAD needs a fallback `symbolic-ref` call. Operation markers are observed before/after inspection and included in the history fingerprint. The initial/refresh page reuses this ref observation, then validates HEAD/refs/boundaries/operation markers after `log`. Ordinary first history page needs five Git launches including discovery, refresh four; a configured, available upstream adds one subsequent comparison call; nested annotated tags and unborn HEAD need extra queries. No loose/packed/reftable ref parser is introduced. Bare repositories remain rejected. Snapshots detect observed changes, not atomic transactions/ABA races.

`WindowsProcessRunner` now launches the requested executable directly with `CreateProcessW` and `STARTUPINFOEX`. A per-command kill-on-close Job Object is attached atomically through `PROC_THREAD_ATTRIBUTE_JOB_LIST`; `HANDLE_LIST` permits inheritance of only stdin/stdout/stderr. Failure to configure ownership fails closed. Both mechanisms are documented for Windows 10+ in [UpdateProcThreadAttribute](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute). There is no per-command .NET helper or persistent service. The existing ProcessHost project is now a library; preview packaging no longer requires a helper EXE/runtime file.

Core still supplies a structured argument array. The small native adapter encodes Windows CRT argument boundaries, supplies an explicit executable/cwd/Unicode environment and never uses a shell. Empty/quoted/backslash/Unicode/metacharacter arguments and environment removal are tested. Standard input is closed; output pipes drain concurrently off-thread. Process exit uses a registered wait; synchronous anonymous-pipe handles use bounded worker I/O. Per-runner concurrency remains two, with one UI read chain. Default output is 256 KiB per stream, history 4 MiB; timeouts remain 15 seconds per command / 45 seconds per UI operation. Cancellation/output overflow closes the job, waits for termination and drains output; normal exit also closes the job to remove leftover descendants. Only owned children are affected. Arbitrary Git/error text remains in memory, never in diagnostic logs. [Windows process creation/handle guidance](https://learn.microsoft.com/en-us/windows/win32/procthread/creating-processes), [pipe inheritance](https://learn.microsoft.com/en-us/windows/win32/ipc/pipe-handle-inheritance) (checked 2026-10-25).

One queued UI read chain cancels and drains obsolete work before the newest read. Tab navigation remains enabled while busy; generation/cancellation/identity checks reject old completions. Per-tab `HistoryViewState` owns the current page, scope, selected row, compact cursors, scroll offsets, timestamp and error/output state. Refresh leaves rows visible. At most three visited tabs retain pages, with a conservative 32 MiB character-data estimate; a single active page is still bounded by the read limit. Each tab retains at most 128 back cursors/page view states; First history page is always available. Eviction clears data and subsequent activation reloads the first page. Nothing preloads other tabs.

Tab activation always validates identity, then skips Git while the cached snapshot is under 30 seconds old. Window reactivation starts validation only when the snapshot is stale. Older snapshots refresh on tab/window activation; Repository → Refresh overrides age. No constant timer/polling or watcher exists; external changes during an active unchanging window require manual refresh. Refresh preserves current page if refs/HEAD are unchanged, otherwise starts at page one. All tabs use All Commits; legacy current-HEAD preferences are ignored without a schema bump. History content/selection/page/scroll remain session-only. Failure/cancellation retains prior rows with stale status. Diagnostics displays bounded in-memory stage durations with localized names (no paths/output); nested timings overlap. Raw Git stderr stays separately in memory.

### Local upstream comparison (F1f, 0.7.0)

`%(upstream)` is captured with the existing ref observation and included in its fingerprint; full symbolic HEAD identifies the corresponding branch without ambiguous short-name matching. After history rows are published, `BranchDivergence` runs `rev-list --left-right --count <HEAD-hash>...<upstream-hash> --`. The two nonnegative invariant integers represent ahead and behind; both buttons compare the configured upstream, not an inferred origin/main or separate push destination. Source: [Git ref fields](https://git-scm.com/docs/git-for-each-ref#Documentation/git-for-each-ref.txt-upstream), [Git rev-list count/symmetric difference](https://git-scm.com/docs/git-rev-list#Documentation/git-rev-list.txt---count), checked 2026-10-25.

This is one bounded worker command (4 KiB per stream, existing 15-second command/45-second chain timeout), never a remote fetch. Immutable tip hashes prevent newer ref tips from being mixed into displayed rows; counts describe the local snapshot, not current server state. Traversal boundaries/config can still change externally; this is not a transactional snapshot. Shallow repositories deliberately report counts unavailable. Missing partial-clone ancestry fails without lazy fetch. Detached/unborn/no-upstream/missing-upstream states do not launch rev-list. There is no persistent count cache or polling: a tab retains one comparison with its page, paging reuses it, and refresh recomputes it. Warm cached switching uses no extra Git call. Generation/cancellation checks reject obsolete completions; count failure leaves rows intact and exposes available raw stderr in Diagnostics. Cancelled comparisons become unavailable rather than remaining pending. The top-center timer distinguishes history reading from comparison work.

### Commit history and graph (through F1f, 0.7.0)

**Diagnosis:** 0.3.x walked only the inspected HEAD and capped expansion at 2,000 commits. No filtering code hid commits. F1c introduced All Commits. In 0.7.0 the user requested one unfiltered workspace: `git log --topo-order --branches --remotes --tags` additionally receives the inspected HEAD hash, so detached HEAD is visible without a selector. Core retains current-HEAD traversal for tests/future filtering, but the UI has no scope controls. Do not substitute `--all`, which includes unrelated refs such as stashes. No reflog traversal, stash-only or unreachable tips are included. [Git log scope and paging options](https://git-scm.com/docs/git-log) (official documentation rechecked 2026-10-24).

`OpenHistoryAsync` captures sorted HEAD/heads/remotes/tags/replacement refs with `for-each-ref` and fingerprints that output plus bounded shallow/graft boundary files. Lightweight and peeled annotated tags map to commits; nested tags are recursively resolved with validated object hashes. Tags pointing to non-commits have no graph row. Ref names remain data; local/remote/tag/HEAD labels are localized, with full labels in details/tooltips. [Git for-each-ref formatting](https://git-scm.com/docs/git-for-each-ref).

`ReadInitialHistoryAsync` reuses the freshly enumerated pre-read fingerprint instead of repeating enumeration; it checks again after reading. Other page reads check before/after. `ReadHistoryPageAsync` reads 200 rows plus one-row lookahead with `--skip` and the expected first hash at each page boundary. A changed snapshot requires explicit refresh; it does not silently combine histories. These checks detect observed changes, not an atomic lock against external clients (an ABA change remains possible). The current-HEAD hash stays pinned; labels are those observed at refresh. All Git, boundary I/O, parsing, graph layout and display formatting run on workers.

There is no total commit-count cap. Only one page of rows/messages is retained; back navigation stores compact offset/lane cursors, bounded to the last 128 visited pages. Each page re-walks earlier commits, so deep offsets cost more CPU and can hit the 15-second command/45-second operation deadline. Output/ref/boundary reads are capped at 4 MiB; graph width at 64 lanes. Page range is visible; full limits are in footer tooltips; failures retain the current page and raw Git errors where available, never masquerading as end-of-history. Missing objects fail without fetching; shallow ends are distinct. Deep-offset optimization and large-history performance remain future measured work.

NUL-delimited UTF-8 metadata retains full messages, parents and original-offset dates. Patches, external diff/textconv, notes, mailmap, decoration and signature helpers remain disabled for these reads. `CommitGraph.BuildPage` carries pending-parent lanes/colors between pages and validates each batch. From 0.4.1 the DataGrid hides column headers, retains resource-backed Header values as cell automation help, and no longer exposes header drag resizing. The fixed-order WPF DataGrid recycles visible rows; graph cells only draw computed segments. Long row subjects/ref labels use bounded prefixes, while selected messages and identities remain complete within the read limit. The message textbox has its own finite scroll viewport. History reserves 300 DIP vertically; the details panel defaults to 180 DIP and can shrink to 80 DIP so small windows retain several commit rows. Existing layout values migrate unchanged to schema 4. Scope help, accessible labels and limits use English resources. In 0.7.0 the table sits flush below tabs; the standard menus and toolbar are above them, with repository/branch/timer in the center. Requested sidebar/toolbar prototypes are disabled with no command and localized help. Original simple path icons are defined in XAML; no Fork assets are used. The history surface uses white/dark and light-yellow same-author text; a runtime high-contrast switch removes custom colors. Exact name/email matching is in CommitRow; WPF text-only triggers leave ref/graph and selected-row colors alone. Complete keyboard/DPI/RTL/high-contrast certification remains deferred.

Tab context menus bind to their placement target, passing a `RepositoryTab` to parameterized view-model commands. Code-behind handles only the middle-button routed event and delegates closing. Active-tab close changes the read generation, cancels work and selects a neighbor; inactive close does not cancel the selected read. Empty selection clears busy state while outstanding owned work still drains before any next read/shutdown.

Page navigation remembers hash/scroll for the bounded back window; tab activation restores its page immediately. A changed-history refresh starts at page one, retaining selection only if present there. Individual ref filtering, search, changed-file/diff views and mutations beyond the F2a actions below remain deferred.

## Authentication bridge (F2b, 0.9.1)

The first authentication increment uses Git/OpenSSH's established askpass protocols, with no external dependency or permanent service. App composes an `AskPassSession` only after an explicit network action is approved. Core receives an `IAuthenticationSession`; WPF stays out of Core. A tiny `Shovel.AskPass.exe` forwards a request to the active operation and writes only the reply to its inherited stdout. It is packaged beside Shovel with its runtime/dependency files; it never runs during history or dialog preparation. Existing credential helpers/agents remain configured, and Git can still store supplied credentials through its configured helper. [Git credential request/helper protocol](https://git-scm.com/docs/gitcredentials) (checked 2026-10-26).

The local pipe uses `CurrentUserOnly`, `FirstPipeInstance`, a random name and 256-bit operation nonce. The client also verifies the server PID. Windows checks the account/elevation level on both ends. Frames are length-checked before allocation: 16 KiB prompt, 4 KiB reply; the UI limits input to 1,024 UTF-16 units and rejects NUL/newline replies. One connection/prompt at a time, at most 16 per operation; connect deadline five seconds and prompt deadline two minutes, within the existing five-minute Git-command deadline. No idle listener, polling or per-history helper. [Pipe options](https://learn.microsoft.com/en-us/dotnet/api/system.io.pipes.pipeoptions?view=net-10.0), [server PID API](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeserverprocessid) (checked 2026-10-26).

Environment endpoint/nonce values pass only to the approved command tree; they are not credentials and expire with the session. This is not a sandbox against same-user processes, trusted hooks/helpers that inherit those values, or a replaced app/helper binary. Request text is untrusted, displayed as plain text with URL redaction; it cannot prove the requesting remote's identity. Responses use PasswordBox/SecurePassword and disposable UTF-8 buffers cleared after send, never view-model string bindings, settings or diagnostics. Temporary OS/native/managed/Git copies cannot be guaranteed erased; configured helper output may itself contain secrets, so raw operation output stays in memory with no automatic export.

For a broker-backed command, standard bundled OpenSSH uses `BatchMode=no`, `StrictHostKeyChecking=ask` and `SSH_ASKPASS_REQUIRE=force`. No automatic host acceptance or known_hosts cleanup. Unknown-host prompts have no structured type in OpenSSH: show the original prompt and require a typed answer instead of guessing from translated text. `SSH_ASKPASS_PROMPT=confirm` has an explicit approval button; `none` is a notification whose helper exit dismisses it without cancelling SSH (for security-key touch). Other helper exit/cancellation closes pending input and stops the operation. Signing and custom SSH commands remain deferred. [OpenSSH environment](https://man.openbsd.org/ssh.1), [askpass hints](https://github.com/openssh/openssh-portable/blob/master/readpass.c), [host confirmation source](https://github.com/openssh/openssh-portable/blob/master/sshconnect.c) (checked 2026-10-26; protocol research, not live interoperability certification).

Git stdin remains closed and `GIT_TERMINAL_PROMPT=0`; ordinary cached GCM usage remains, but `GCM_INTERACTIVE=never` continues to suppress its GUI/browser prompts. Credential debug/trace environment is suppressed for explicit actions. Browser sign-in needs a tracked external-interaction lifecycle before enabling it: the current job boundary must not terminate a newly launched browser. GCM's official interactive and modal-parent options are candidates for that later route, not enabled behavior. [GCM environment documentation](https://github.com/git-ecosystem/git-credential-manager/blob/main/docs/environment.md) (checked 2026-10-26). No global Git/credential-store configuration is changed.

The operation model publishes a known input-wait state only while its prompt callback is active. Cancelling or expiring a prompt cancels the owned operation; disposal waits for the prompt broker before reconciliation/navigation resumes. Pipe failure, timeout and request-limit outcomes have localized explanations. Existing shutdown/modal admission, repository mutex, state revalidation and post-attempt refresh remain unchanged. No interactive UI or live account was used for development verification; roadmap records headless evidence and remaining gates.

## Explicit Git actions (F2a, 0.8.0)

`GitActions` prepares an immutable action context off-thread: filesystem identity, HEAD/ref snapshot, effective fetch/push addresses and a hash of effective configuration (not stored/logged). These extra commands run only on explicit dialog opening, never startup. Remote metadata is capped at 32 remotes and single fetch/push URL per remote; unsupported configurations fail with guidance. `GitActionViewModel` owns editable options and one attempted operation per dialog. `ShellActions` holds UI admission closed, invalidates linked-worktree caches and forces normal history inspection after success, failure or cancellation. Preparation failure does not start an action.

Execution requires a per-operation approval for repository-controlled hooks/filters/credential helpers, separately from automatic history. Before commands, reread identity, paths, HEAD/refs and config hash; reject changes and in-progress sequences. A named mutex keyed by the common Git directory coordinates Shovel processes in this Windows login session. Acquire/release occur on the same worker thread; abandoned ownership triggers the same fresh validation. Different Windows sessions, external Git clients, path aliases and edits between checks/command launch remain outside this lock. Git's own locks remain authoritative; no lock files are removed. Neither identity nor config hashes attest the contents of executable hooks/helpers or protect against hostile atomic replacement.

New branch uses `branch --no-track` or `switch --create --no-track`, with a validated name and immutable starting hash; duplicate branches fail. Switch uses `--no-guess` and never force/discard. Switch and Pull pass `--no-overwrite-ignore`, protecting ignored-file collisions as well as checked dirty state. Checkout and Pull reject dirty/untracked state, submodule repositories and sparse-checkout files; linked-worktree branch occupancy is enforced by Git. Fetch names its remote and explicit `+refs/heads/*:refs/remotes/<remote>/*` mapping with empty `--refmap=`, no pruning or recursive submodules. Rewritten remote tips update only their tracking refs; the dialog explains this. Pull fetches a selected branch, rechecks local HEAD/config/identity/clean state, cross-checks FETCH_HEAD against the fetched tracking tip and runs `merge --ff-only --no-autostash --no-edit`. Nonempty branch.mergeOptions are rejected before fetching because they can change the promised fast-forward behavior (for example, squash). Configuration is not edited. This is deliberately a two-command operation: a failed fast-forward can leave fetched objects/refs. External clients can race between checks; the two commands are not a transaction.

Push supplies explicit source/destination refs, disables implicit mirror/follow-tags/submodule pushing, and never forces. Tags and upstream setup require explicit options. Git pre-push/checkout/merge hooks and configured filters are not bypassed. Push of multiple refs or sequential fetch-all can partially succeed; no atomic rollback is claimed. Current installed Git 2.51.1 is tested using local bare remotes. Official command semantics checked 2026-10-25: [fetch ref mappings](https://git-scm.com/docs/git-fetch), [fast-forward merges](https://git-scm.com/docs/git-merge), [push destinations/hooks/upstream](https://git-scm.com/docs/git-push), [switch/create and worktrees](https://git-scm.com/docs/git-switch). These sources describe Git, not verification of every auth provider or Git version.

Writes reuse the job-contained async runner with a five-minute per-command deadline and 1 MiB output cap. Stream decoding/redaction runs off the dispatcher; output is retained only in modal memory. Userinfo/query secrets in HTTP(S) URLs are redacted; arbitrary trusted-helper output cannot be comprehensively classified as secret and must not be persisted/exported automatically. Progress reports running, duration and explicit cancellation, never guesses an input wait from silence. Cancellation kills only owned job descendants and is not undo. Partial output and state remain inspectable; no retry is automatic.

**Authentication:** F2b above supersedes the original cached-only F2a limitation with an operation-scoped askpass bridge. Without a broker, the Core action service retains noninteractive execution and strict known-host behavior. Custom core.sshCommand and unrecognized bundled SSH layouts still fail explicitly. The command defaults to denying other transports while explicitly allowing file/http/https/ssh/git; Git may honor an explicitly configured per-protocol permission, so execution approval includes repository transport helpers. Startup reads still request no network/helpers.

`CommitRef.Upstream` reuses the existing ref query, adding no startup subprocess. `RefBadge` combines only the configured same-tip upstream; full names and current-branch meaning remain in accessible help. Original vector paths inherit row/system colors and preserve virtualization/author highlighting. No provider logos, avatars or additional network assets are used.

## Settings, storage, localization

**Implemented:** schema-4 settings under `%LOCALAPPDATA%\GitGui\Foundation` (or an explicit absolute test-profile path), separate from binaries. Stores layout/navigation and up to 20 absolute repository paths in tab order with selection, per-tab scope and path/identity stamps for replacement detection; paths are local private data. Schemas 1/2/3 migrate without any read-consent requirement; saving preserves previous bytes in the backup. Reads/writes are limited to 64 KiB and values normalized. Saves use a same-directory temporary file, cancellation check, atomic move/replace and previous-file backup; changed input since load blocks saving. This detects external edits but is not an atomic transaction with arbitrary editors. Invalid/newer/unsupported schemas and unavailable files remain untouched. [README](../README.md#local-data-and-recovery) owns file names and recovery instructions.

Diagnostics accept only typed event/failure codes and UTC timestamps, through a 128-entry bounded queue. Two rotating files retain roughly 512 KiB total, with at most one event of threshold overshoot; overload drops events. No exception text, stack traces, credentials or repository content enter the log. Worker-task logging failure is nonfatal. This is a safe foundation, not comprehensive crash reporting.

**Deferred settings fields:** drafts, tool definitions, update preferences and redacted recovery markers. No credentials. Future caches must be bounded and rebuildable. On restart rediscover Git state before enabling mutations; no automatic command replay.

**Migration policy:** validate before writing; preserve pre-migration bytes as the backup during atomic replacement. Never overwrite a newer/invalid schema. Schemas 1/2/3-to-4 migration exists; no general migration engine or in-app recovery/export UI. Older previews open newer schemas read-only; reverting binaries does not restore data automatically. Separate channel profiles if pilot schemas diverge. The product name is Shovel; publisher, installation identity and the permanent data path remain undecided; the current Foundation profile is provisional.

**Implemented localization:** neutral English `.resx` messages, ResourceManager lookup, `{loc:Text Key=...}` in XAML and UiText lookup/formatting in view models/lifecycle. Whole messages replace concatenation; formatting uses the user's CurrentCulture while UI language is currently English. Window flow direction derives from UI culture; the version is direction-isolated. Accessibility names use localized labels, not model ToString output. Built-in OS dialog button captions are supplied by Windows.

**Deferred:** language selection/satellite resources, a plural-aware formatter before the first count message, pseudo-localization/RTL verification, theme selection and installer/updater resources. Inspection dates/durations use CurrentCulture; repository paths/hashes and raw output have LTR fields. Complete bidi isolation of mixed branch/path messages still needs verification. Do not use the Framework-only LocBaml workflow for modern WPF. [WPF localization](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/wpf-globalization-and-localization-overview).

## Updater comparison: current official evidence

WPF has no built-in universal updater. A compatible third-party framework is distinct from Microsoft platform support. Final choice requires installed upgrade, idle-gate, signature and localization tests; documentation alone is not proof.

| Option | Fit, signing and installation | Tradeoff / decision status |
| --- | --- | --- |
| **NetSparkle + per-user installer** | .NET/WPF support; static appcast; strict Ed25519 verification for both feed and package. Separate installer handles replacement. | Strong candidate for exact consent flow and signed manifest requirement. App owns scheduling/idle coordination; installer must prove safe in-place repair and failure handling. No automatic rollback assumed. |
| **Velopack** | C# SDK, static hosting, integrated packaging/update lifecycle, LocalAppData installation; code-signing support. | Strong candidate for less installer machinery. Must verify complete feed/package authenticity and signer policy in pinned version, not assume hashes or signed EXEs authenticate every package byte. Automatic pending-update application on startup is documented as enabled by default and must be disabled. |
| **MSIX / App Installer** | Windows-managed signed packages and update deployment; package certificate must be trusted on each device. Supports packaged desktop apps. Per-user deployment is feasible under device policy. | Attractive with company-managed certificate trust. App Installer scheduling is not our Git-aware idle gate; automatic background/opportune application may conflict with explicit restart consent. Programmatic deployment needs a proven integration; no forced shutdown/activation blocking. |

NetSparkle's documented strict mode requires a detached appcast signature and a signature on the downloaded package; it does not supply the installer. Proposed packaging companion: NSIS, user execution level, offline self-contained runtime, fixed application identity, no forced closing of tracked processes. This is a candidate, not a selected bundle. [NetSparkle official README](https://github.com/NetSparkleUpdater/NetSparkle), [NSIS user privilege option](https://nsis.sourceforge.io/Reference/RequestExecutionLevel).

Velopack supports static file distribution and C# integration. Its installation directory is replaced during updating, so user data must live elsewhere. Inspect all auto-apply/exit behaviors and preserve explicit consent. [Introduction](https://docs.velopack.io/), [integration/default auto-apply](https://docs.velopack.io/integrating/overview), [installer](https://docs.velopack.io/packaging/installer), [signing](https://docs.velopack.io/packaging/signing), [preserving data](https://docs.velopack.io/integrating/preserved-files).

App Installer options have different minimum Windows versions; its independent background check runs every eight hours rather than an arbitrary in-app interval. Do not enable UpdateBlocksActivation. OS package-in-use detection cannot identify a Git conflict workflow after processes exit. Programmatic non-Store updates are possible, but compatibility with the full consent/idle flow must be tested. [Update settings](https://learn.microsoft.com/en-us/windows/msix/app-installer/update-settings), [programmatic updates](https://learn.microsoft.com/en-us/windows/msix/non-store-developer-updates), [servicing while in use](https://devblogs.microsoft.com/insidemsix/msix-servicing-while-in-use/).

MSIX signing requires device trust; self-signed/internal certificates need provisioning, potentially IT/admin involvement. Publisher identity and certificate rotation need a deployment plan. App Installer availability, sideload policy and target Windows build must be checked. Windows code signing does not guarantee no SmartScreen prompt. [Microsoft signing guidance](https://learn.microsoft.com/en-us/windows/msix/package/signing-package-overview), [App Installer troubleshooting](https://learn.microsoft.com/en-us/windows/msix/app-installer/troubleshoot-appinstaller-issues).

## Proposed update mechanics

Use the selected framework's manifest format (for example signed appcast), not an invented wire protocol. Required fields are U2; propose channel, OS/architecture, minimum version/schema compatibility, package size/hash, signer/key identifier, and release-note content covered by verification. Allow only supported schema/HTTPS locations; reject unexpected redirects/auth pages and downgrade/replay below installed or persisted trusted version. Signature verification must precede executable use; checksums additionally detect corruption. Do not render active HTML from release notes.

Check after shell startup, with timeout/backoff; optional periodic interval never overlaps a check. Download to bounded staging storage and re-verify completed bytes after resume. Cancellation discards or quarantines partial data. Do not install on download completion, ordinary close, or next startup.

On explicit Restart and update: acquire an app-wide shutdown/update gate across instances, stop admission of new work, recheck every repository/operation/tool/prompt and unresolved sequence, persist session safely, then hand off to the updater only if idle. Unknown tool lifecycle blocks until completion is verified or acknowledged. The installer must not force-kill an instance or race a new launch. Revalidate package identity/signature at handoff. Startup recovery still blocks installation when Git has unresolved work. Failure to persist state cancels shutdown.

### Signing and bad-release recovery

Updater signature (e.g. Ed25519) authenticates downloaded feed/package against a bundled public trust key. Authenticode/MSIX signing establishes Windows publisher trust; HTTPS authenticates transport. These are separate controls; neither a hash nor an updater signature replaces Windows certificate trust.

Keep private keys outside repository, app, artifacts and ordinary logs; restrict release access, use protected signing/CI or hardware-backed storage, and document backup/rotation/compromise handling. Public verification keys may ship. No keys/providers are selected or generated; signing-service eligibility/budget and company certificate trust remain open.

Retain known-good artifacts and schema backups. Pilot first; if bad, withdraw manifest, keep clients operational, and publish a higher-version corrective release compatible with affected schemas. Maintain a separately reachable signed repair installer for an app that cannot start. Repair must not require routine uninstall/reinstall; exceptional downgrade/data restore is an explicit documented procedure. No automatic rollback or power-loss atomicity claim without implementation evidence.

## Hosting and release operations

| Hosting | Availability/maintenance | Outside office and access |
| --- | --- | --- |
| Personal computer | Least dependable: sleep, restart, changing address, bandwidth and owner availability; TLS/backups/security upkeep required | Office/VPN-only unless intentionally exposed through managed HTTPS networking. NAT/firewall/DNS and a reachable trusted certificate are prerequisites, not something to configure silently. |
| Company server | Good if already monitored, backed up and maintained; still an outage dependency for new downloads | Internal endpoint requires corporate network/VPN and DNS/certificate trust. External users need approved public HTTPS access or VPN; browser login alone does not authorize an updater. |
| Managed static/object hosting | Preferred proposal for low operational effort; storage/egress cost and provider policy remain | Public HTTPS supports offsite access without VPN. Private packages require supported per-user authentication/access gateway or approved private networking; test proxy and token expiry behavior. |

Do not equate unlisted URLs with private distribution. Some static website products are public-only: Azure Storage's static website endpoint does not support authentication/authorization; private deployment needs a suitable endpoint/service. [Official Azure hosting limitations](https://learn.microsoft.com/en-us/azure/storage/blobs/storage-blob-static-website). Reuse existing company identity where possible; never embed a PAT/shared password. Exact host/access integration is open. Unavailable hosting affects only update discovery/download, never installed local functionality.

Proposed release sequence: build/test -> sign immutable versioned packages -> upload packages and signed notes/metadata -> verify downloads from user-facing endpoint -> test-channel promotion/pilot -> atomically publish stable manifest and matching signature. If atomic pair publication is unavailable, mismatch must fail closed and retry later; never relax verification. Use short manifest cache lifetime, immutable artifact URLs, retain prior packages. Prepare a release checklist, licenses, migration/recovery notes and standard-user upgrade report before distribution.
