# Independent Rust application

The owner requested the entire Shovel desktop application in Rust on 2026-11-05. Baseline C# source is `2175458` (0.47.0). This branch is in progress and has no delivered Rust application yet. [TODO](../TODO.md#entire-rust-application--active-not-delivered) owns the complete parity checklist; historical C# milestones are not Rust evidence.

The Rust workspace uses a pinned MSVC toolchain with core, desktop and askpass crates. The desktop uses egui/eframe 0.37.0 with native Windows/WGPU rendering, AccessKit and system fonts. It does not use a browser or start the C# application. The internal workspace currently wires repository opening/restoration, asynchronous history paging, graph/metadata/file comparisons, working-copy staging/hunks/Commit/drafts, explicit Fetch/Pull/Push, local branches/reviewed checkout, history Reset/Revert, sequence recovery, saved-stash workflows, inline conflict resolution and profile saving; it is not the complete application. Git for Windows remains the configured Git engine so hooks, filters, credentials and tools retain their native behavior. Existing C# source/assets/resources serve as the parity reference and are excluded from the Rust runtime package.

## Network and authentication ownership

Cached split-button options do no Git or filesystem work. Changed flags are saved asynchronously even when the menu is dismissed; explicit destinations retain the reviewed branch, while implicit destinations resolve current Git configuration when executing. Accepted requests belong to the application scheduler, with Fetch separate from working-copy mutations and Pull/Push exclusive across the shared repository. The captured identity/branch/HEAD guard remains; a queued request whose HEAD changes before its worker starts currently fails with a stale-state explanation. This needs further parity review for queues following another accepted commit.

The native network layer validates configuration and refs, uses shared C#/Rust named mutation locks, suppresses implicit pruning/recursion/force/mirror behavior and retains partial results. Pull also owns the Fetch lock through immutable FETCH_HEAD/tracking-tip verification and merge/rebase; ignored-path collisions and zero-exit autostash conflicts remain visible. Captured output is bounded and URL-redacted before presentation; arbitrary raw pipe chunks are not exposed as a credential-redaction boundary. Read failures after a successful native command remain separate from that command's actual outcome.

`ShovelRustAskPass.exe` uses a per-operation current-user Windows pipe, random nonce and server-PID verification. Overlapped I/O drains before buffers/handles are released, with bounded prompts/replies and a two-minute prompt deadline. The implementation follows Microsoft's [pipe access-control](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights) and [overlapped-I/O lifetime](https://learn.microsoft.com/en-us/windows/win32/ipc/synchronous-and-overlapped-input-and-output) documentation, checked 2026-11-05. The Rust UI masks replies, clears editor undo state, supplies SSH confirmation/information responses, and closes prompts when their broker ends. Declining or timing out supplies no answer; it never kills an accepted Git command. No credential/prompt persistence is added. Actual GCM/SSH accounts, security-key interactions, native modal ownership/focus and the complete authentication appearance remain unverified.

## Local branches and checkout

Branch options use cached refs and do no preparation on opening. Create uses an immutable start commit and disables inherited upstream setup; switching and detached history checkout enter a review window that requests its local scan only after visible layout. The confirmation captures index/config/HEAD/branch/identity and named-target state. Unrelated fetched refs do not invalidate checkout. Keep uses native overwrite protection; stash/reapply includes untracked files and restores the index, retaining recovery data on hook/apply failure or a changed stash stack. Tracked discard lists its reviewed paths and requires the dedicated destructive confirmation, preserving untracked/ignored paths and non-recursive submodule behavior.

Delete confirms the fixed repository, full branch name and tip before submission. Set/unset upstream use existing local remote-tracking refs without network access; native merged/current/linked-worktree guards and direct-ref/config checks remain. The shared operation controller retains accepted work after dialogs close and refreshes the originating repository. Retained Commit views coalesce an external refresh, defer closed-view reads until reopening and keep their draft text. Successful work with a retained recovery stash carries a visible warning separately from command or reconciliation failure. No running-command cancellation or recovery rollback is introduced. Native modal ownership/focus, final appearance, full keyboard navigation, LFS/sparse/submodule scenario coverage and complete R47–R49 acceptance remain open.

## History actions and sequence recovery

History menus capture the row's full commit hash without Git preparation. Reset confirms the fixed repository, branch, previous tip, target and distinct Soft/Mixed/Hard effects; native reset retains its documented untracked-obstruction behavior and disables recursive submodule updates. The worker revalidates identity, HEAD, configuration, references and linked-worktree occupancy. Revert validates original commit-object parents, requires an explicit merge mainline, uses Git's existing message, retains hooks/signing, and reports native conflicts or partial hook failure without rollback. Detached checkout continues through the reviewed checkout workflow.

Snapshots include bounded sequence metadata for merge/rebase/cherry-pick/revert. Fixed state files are limited to 256 KiB each; mailbox, ambiguous and oversized state has no enabled recovery target. Only validated hashes and branch names enter target labels. Continue rejects unresolved stages, preserves the existing message and native hooks/signing/rebase exec commands. Skip/Abort require specific repository/sequence/target confirmations. Execution compares identity, HEAD, branch, sequence state and a freshly observed semantic index; staging resolutions does not invalidate the displayed sequence. No refs, remotes or whole-worktree scan is required before a recovery command. Accepted work survives dialog closure; remaining sequence/conflict state is retained visibly after reconciliation.

These paths have focused native-Git and headless confirmation evidence, not complete R60/R61 acceptance. Native menu/keyboard/focus/appearance, broader filter/LFS/submodule/signing/account scenarios and other sidebar/Repository-menu entry points remain open. The goal remains active and unpublished.

## Saved stashes

The resizable Stashes window retains the local list, selected hash and message across reopening, starts reads only after visible layout, and keeps useful rows after failed refresh while disabling mutations from that failed list. Selection follows the hash when reflog ordinals change. Immutable tracked/index/unstaged/untracked comparisons share the existing diff viewer and preserve saved metadata; closing cancels display reads without cancelling accepted work. Closed comparison state is released, with at most three retained list caches. Only an unchanged submitted Create message is cleared after successful completion.

Create uses native stash push with optional untracked files; ignored files and recursive submodule mutation are excluded. Apply/Pop use the selected hash and optional index restoration. Drop confirms the frozen repository/selector/hash/message. Execution validates identity, HEAD, index/conflict state and the reviewed stash list; Pop applies once, verifies conflict state and rechecks the list before dropping. Drift or failed removal reports applied content separately and retains a clear warning against blindly applying again. Drop reports its own native result even when pre-existing conflicts or a sequence remain unchanged. History/sidebar stash menus use cached targets and the same worker; they do not expose reset/revert as stash actions.

Native ownership/keyboard/appearance, geometry persistence and broader filters/LFS/submodule/large-list scenarios are still open. These implementations and focused tests do not complete R58/R59 acceptance.

## Inline conflict resolution

Local Changes opens the selected conflicted path inline. Stage 1/2/3 objects and actual merge/rebase provenance determine the named source panes; side checkboxes only change the preview. Resolve and stage explicitly applies one native side (including deletion) or the edited result, then stages that path. Other unresolved files and the current sequence remain pending. Captured identity, HEAD/branch/sequence, semantic index, effective configuration/attributes and working-file bytes are checked before execution under the shared mutation mutex. External Git clients remain outside that mutex.

Edited text strictly preserves UTF-8 or BOM-marked UTF-16 LE/BE, including byte order, transport BOM and existing line endings. The 512-KiB encoded limit includes the BOM; 20,000 newline and 16,384 UTF-16-unit column limits match the baseline. Unsupported binary/LFS, malformed Unicode, transformations and residual conflict markers cannot be saved as edited text. Native side/tool resolution remains available for supported regular binary files. Edited results use a same-directory temporary write/flush/revalidation/atomic replacement, followed by native add. Failed staging leaves saved bytes in place and retains editor text, status and redacted output for review; no automatic rollback/retry occurs.

The merge-tool selector uses cached built-in/configured names and copied saved preferences. It performs no executable discovery when opened. Submission validates the selected default/named/executable/custom command, uses per-process overrides and native Git mergetool variables, and checks actual unmerged stages afterward without changing Git configuration or adding consent gates. Accepted resolution/tool work belongs to the repository scheduler, survives closing the Commit window and prevents app exit until it drains. Cancelling display reads does not cancel an accepted command. The app asks before discarding unsaved editor text on file navigation, view close or exit; cancelling keeps that text, while confirming never removes already-written file content. App exit resumes its settings save after the unsaved-text decision.

These are partial R62–R64 implementations with focused Git/headless interaction evidence. Native visual/keyboard/accessibility parity, saved conflict-pane proportions, broader LFS/filter/stash provenance/linked-worktree scenarios, real GUI merge tools and detaching-tool behavior remain unverified. They do not complete these acceptance rows or authorize publishing a partial application.

## Selected local files and discard

The Local Changes menu captures selected/all rows without Git or filesystem preparation, preserves multiselection and defers selection diffs until it closes. Stage/Unstage, relative/full path copying, Enter/Shift+Enter, Ctrl+Shift+Alt+S, Ctrl+C/Ctrl+Shift+C and Delete use the displayed selection. Discard confirms the actual repository, HEAD, paths/rename endpoints and per-target effects; a replaced snapshot invalidates acceptance. Confirmed work uses the repository scheduler and survives closing the editor.

The worker validates identity, HEAD/sequence, semantic index, effective configuration and selected rows under the shared mutation mutex. Unstaged files use native `checkout-index --index --force --stdin -z`, preserving staged bytes, smudge/LFS and index hooks without post-checkout. Staged files restore index/worktree from captured HEAD; unborn and selected untracked files use exact nonrecursive deletion. Windows `DeleteFileW` preserves read-only/sharing failures. Partial native/filesystem results retain actual counts, redacted output and refreshed rows without retry or rollback. Native success with remaining selected changes is explicitly distinguished from a clean result. Git [checkout-index](https://git-scm.com/docs/git-checkout-index), [restore](https://git-scm.com/docs/git-restore) and Windows [DeleteFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-deletefilew) contracts were checked 2026-11-05.

For a bounded standard-LFS modified subset, reconciliation validates index flags/attributes and hashes local bytes against immutable pointer objects independently of Git's stat cache. This retains same-size/time edits made by checkout hooks and missing-object failures. Unsupported transforms, pointers and index flags fall back to ordinary status; this is not a claim that all tracked files are hashed during every read. Reconciliation currently performs a full working-copy read; targeted responsiveness parity remains open.

Selected Stash confirms frozen paths and an optional UTF-8 message, then builds a private HEAD-based index containing only selected staged entries. The private index lives beside the real index for split-index compatibility; semantic validation ignores harmless stat refresh. Native path-limited stash captures selected working/untracked content and the selected index parent. Only after an actual new saved entry and revalidated real state does native restore reset the selected real index entries. Unrelated staged/worktree content is retained, including when the saved stash is later applied with `--index` in a clean worktree. Saved hashes, native failures and later reset failures remain visible; no retry/drop/rollback follows a partial outcome. Accepted work survives view closure. [Native stash semantics](https://git-scm.com/docs/git-stash), [write-tree](https://git-scm.com/docs/git-write-tree) and [read-tree](https://git-scm.com/docs/git-read-tree) were checked 2026-11-05.

Git 2.51.1 can save a selected staged rename/deletion and then fail its internal cleanup because an absent path no longer matches its private index. Rust reports that failure and retained saved hash, preserving the current real index/worktree. This native limitation is verified rather than hidden by extra cleanup. R42–R46 remain incomplete: Open/Explorer, External Diff, rules, patch export and file inspection are still pending. Native clipboard behavior, long-target confirmation layout, keyboard/appearance/accessibility, broader filter/linked-worktree cases and efficient targeted reconciliation are not certified. No additional acceptance row is marked complete.

## Independent channels

`distribution/rust-channels.json` defines `ShovelRust`, `ShovelRust.exe`, the independent `ShovelRust/Foundation` profile, `codex/rust-rewrite` development and `codex/rust-beta` / `codex/rust-stable` release branches. All three branches exist locally; the release branches initially point to foundation commit `01c7593`. Beta is the initial channel. Importing C# preferences copies into the Rust profile and translates the update preference; it never writes the C# profile or shares updater trust files. Draft import copies into independent Rust storage; complete nested preference normalization remains pending.

Both Rust channels use dedicated feed tags, never GitHub `latest` or C# `beta`. Both are GitHub prereleases with `make_latest=false`, including future Rust Stable: the user-facing stable channel is defined by its signed feed, while GitHub latest remains exclusively the C# client's Stable endpoint. Stable's feed location is reserved, with no public assets until approved. Existing public-key identity signs a distinct Rust envelope containing product, channel, architecture, source commit and the Velopack asset; consumers verify signature and all identities before deriving a download URL. Reusing the publisher key does not authorize cross-product packages.

Release packages and profiles use `ShovelRust` to coexist with `Shovel`. Beta/Stable share only the Rust installation identity, with Rust-only channel changes and no downgrade. Versions come from workspace Cargo metadata; C# `Directory.Build.props` remains unchanged. Native installer/updater integration uses Velopack's Rust SDK, not its C# application host. The upstream [Rust integration](https://docs.velopack.io/getting-started/rust) was checked 2026-11-05; packaging/tool compatibility must be verified against the pinned actual crate.
